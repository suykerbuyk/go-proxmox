# Migrating to v0.8.2

v0.8.2 makes the client return an error for every non-2xx response. Before
it, only 400, 401, 403, 500 and 501 were errors. Every other status (404,
409, 502, 503, 504, and Proxmox's own 595-599 "cannot reach that node"
range) was decoded as if it had succeeded. A `{"data":null}` body left the
result at its zero value, and the call returned a nil error.

## TL;DR

No source-level break. `StatusError`, `ShapeError` and `ErrUnexpectedShape`
are new exported names, and no existing signature changes. The change is in behaviour: calls that used to return a
zero value with a nil error now return an error.

| Change | Affected callers | Fix |
|---|---|---|
| any non-2xx now returns `*proxmox.StatusError` | callers that relied on a zero value from a failed call | handle the error; branch with `errors.As`, `IsNotFound` or `IsNotAuthorized` |
| 400, 500 and 501 errors are now `*proxmox.StatusError` | callers that type-assert these errors | use `errors.As`; the `Error()` text is unchanged |
| deleting a cloud-init VM refuses when an ISO lookup fails and the storage's content listing cannot confirm the ISO is absent, or when the ISO's delete task fails | `VirtualMachine.Delete`, `UnmountCloudInitISO` | see "Deleting a cloud-init VM can now refuse" |
| guest ipset deletes now send `force` and `digest` | `DeleteFirewallIPSet` and `DeleteFirewallIPSetEntry` on `VirtualMachine` and `Container` | a stale `digest` is now refused; pass `""` to delete without the check |
| `Client.DeleteTFAEntry` now sends its password | callers deleting another user's TFA entry | the password now reaches PVE, and pveproxy's access log records it (see "DeleteTFAEntry now sends its password") |
| a task that ended `WARNINGS: <n>` is now `IsSuccessful`, not `IsFailed` | callers of `Task.Ping`, `Wait` and `WaitForCompleteStatus` that read those flags | none, unless warnings must count as failure: then check `ExitStatus` |
| `AgentExec` returns its POST's error | callers that matched "no pid returned" | handle the error; `errors.As` reaches the `*proxmox.StatusError` |
| `Storage.ISO`, `VzTmpl`, `Import` and `Backup`, `Node.Storage`, and `AgentExecStatus` return an error on `{"data":null}`, where they (or `WaitForAgentExecExit`) panicked | callers of those getters | handle the error; it does not match `IsNotFound` |
| a field of the wrong JSON type in a task status, `/cluster/status` or a task log is a `*proxmox.ShapeError`, where decoding panicked; a `/cluster/status` entry with no `type` is one too, where the rest of the list was silently dropped | callers of `Task.Ping`, `Wait`, `WaitFor`, `Client.Cluster`, `Cluster.Status`, `Task.Log` | handle the error; `errors.Is(err, proxmox.ErrUnexpectedShape)` |
| `TermWebSocket` and `VNCWebSocket` no longer panic when the client has no `Transport`, a custom `RoundTripper`, or `WithRetry` | ticket-authenticated WebSocket callers | none; with `WithRetry` the TLS options now reach the WebSocket dial |

## What callers will newly see

- **`Client.Node` on an offline node** now returns an error from its status
  read. It still returns the `*Node`, as it did for any other error.
- **List and get calls against an unreachable node** (`Node.VirtualMachines`,
  `Node.Storages`, `Cluster.Resources` and the rest) return an error, not an
  empty list or a zero-valued struct. Several single-object getters, such as
  `Node.VirtualMachine`, `Node.Container` and `Storage.ISO`, used to panic
  on a nil result here. They now return the error.
- **Writes that pass a nil response target**, and task-returning calls such
  as `VirtualMachine.Start`, used to report success on 404, 5xx and 59x.
  They now return the error, instead of a nil `*Task` and a nil error.
- **`Task.Wait`** no longer reports a task as finished when its status poll
  failed.
- **`Cluster.CheckID`** no longer reports a VMID as free when the check
  itself failed.
- **`UploadReader`** on 401 or 403 now returns an error that
  `IsNotAuthorized` matches, instead of a nil error.

## Branching on the status

```go
var se *proxmox.StatusError
if errors.As(err, &se) {
    // se.StatusCode, e.g. 595
    // se.Status, e.g. "595 Connection refused" (Proxmox puts its message in
    //   the reason phrase)
    // se.Body, the raw response body, which can carry detail the
    //   reason phrase does not
}

proxmox.IsNotFound(err)      // true for a 404
proxmox.IsNotAuthorized(err) // true for a 401 or 403
```

`IsNotFound` is **not** a test for "the object does not exist". Proxmox
reports a missing VM, storage, volume or pool as a **500**, with the message
in the reason phrase. A 404 usually means a wrong API path, or a proxy in
front of Proxmox.

The library adds no retry and no "treat as absent" policy. When `WithRetry`
is enabled, it still retries below this layer (by default on 429, 502, 503
and 504). A status that is still failing after the retries now reaches the
caller as a `*StatusError`.

## Unchanged

- The `Error()` text of the 400, 500 and 501 errors, byte for byte. Code that
  matches on it, for example `"500 QEMU guest agent is not running"`, keeps
  working.
- A 400 whose body is not JSON still returns the JSON decode error's text.
  `errors.As` also still reaches the underlying `*json.SyntaxError`.
- 2xx handling, including a `200 {"data":null}`: that still decodes to a zero
  value with a nil error. Whether null is acceptable there is the caller's
  decision.
- The 401/403 re-authentication in `Client.Req`, which still returns
  `ErrNotAuthorized` itself.

## Deleting a cloud-init VM can now refuse

`VirtualMachine.Delete` and `UnmountCloudInitISO` remove the VM's cloud-init
ISO from whichever iso-capable storage holds it. Before v0.8.2, a failed
lookup on a storage was treated as "not on this storage". If that storage
held the ISO, the VM was deleted and the ISO was left behind.

When a lookup fails, the storage's content listing now decides. `Delete`
returns an error, and sends no VM DELETE, when a lookup fails and:

- the listing shows the ISO, so the lookup failed on something that exists;
- the listing cannot be read, for example an unreachable NFS mount that is
  still enabled in the storage configuration;
- the listing comes back with no data at all (`{"data":null}`).

This is deliberate: deleting the VM cannot be undone, and the storage that
could not be confirmed may hold the ISO. Disable a storage that is
permanently unreachable, or fix it, then retry the delete.

`Delete` and `UnmountCloudInitISO` also refuse when the ISO's delete task
stops without succeeding. They used to check only that the task had stopped,
so a failed ISO delete was followed by the VM delete and the ISO was left
behind. A task that completed with warnings (`WARNINGS: <n>`) is a success,
as Proxmox counts it. `Task.Wait` itself is unchanged: it still returns once
a task stops, however it ended.

Unchanged: a lookup that finds the ISO deletes it, and an ISO that neither
the lookup nor the listing finds is treated as already gone.

## Guest ipset deletes now send force and digest

`VirtualMachine.DeleteFirewallIPSet`, `Container.DeleteFirewallIPSet` and
their `DeleteFirewallIPSetEntry` siblings never sent their parameters: the
map was passed as the response target. They now send `force=1` when `force`
is true, and `digest` when it is not empty.

- A forced delete of a non-empty ipset now succeeds, where PVE used to refuse
  it.
- A non-empty `digest` is now checked. A stale one makes PVE refuse the
  delete, where the entry used to be deleted regardless. Pass `""` to delete
  without the check.

## AgentExec returns its own error

`VirtualMachine.AgentExec` discarded the error from its POST and reported
"no pid returned from agent exec command" instead. It now returns the POST's
error, a `*StatusError` for a non-2xx reply. A pid that is not a number is
now an error, where it used to panic.

## Getters no longer panic on an empty reply

`Storage.ISO`, `Storage.VzTmpl`, `Storage.Import`, `Storage.Backup` and
`Node.Storage` dereferenced a nil result, and panicked, when their read
succeeded with `{"data":null}`. So did `WaitForAgentExecExit`, on
`AgentExecStatus`'s nil result. They now return an error. It does not match `IsNotFound`:
an empty reply is not evidence that the volume is absent. Deleting a
cloud-init VM treats this error like any failed lookup, and lets the
storage's content listing decide.

## DeleteTFAEntry now sends its password

`Client.DeleteTFAEntry` passed its password as the response target, so it was
never sent. It is now sent as the `password` query parameter: PVE reads a
DELETE's parameters from the query string only. pveproxy writes each request
line, query included, to its access log, so the password appears there.

## A task that ended with warnings is a success

`Task.Ping` set `IsFailed` on any exit status but `OK`, so a task that
completed but logged warnings (`WARNINGS: <n>`) read as failed. It now sets
`IsSuccessful` for it, by Proxmox's own rule (`PVE::UPID::status_is_error`).
`ExitStatus` still carries the text, for a caller that must tell the two apart.

## Decoders return a ShapeError instead of panicking

`Task`, `Cluster` (`/cluster/status`) and `Log` decoded some fields by
asserting their type, and panicked on a value of any other type, `null`
included. A value of the wrong type is now a `*proxmox.ShapeError` naming the
type, the field, and the JSON kinds wanted and found;
`errors.Is(err, proxmox.ErrUnexpectedShape)` matches it. A `null` or absent
field leaves the field at its zero value, as `encoding/json` does.

A `/cluster/status` entry with no `type` used to end decoding and drop every
entry after it, with no error, so a caller saw fewer nodes. It is now a
`ShapeError` whose field names the entry's index (`[1].type`); an error in
any other field of an entry names it the same way (`[1].online`). On any of
these errors the `Cluster` may be left partly filled, with the entries before
the bad one: ignore the value when the error is not nil.

A task log row is read only when it carries both `n` and `t`, non-null; a row
with just one of them is skipped whatever its type, as it always was.

## WebSockets no longer panic on the client's transport

`TermWebSocket` and `VNCWebSocket` asserted the client's `Transport` to be an
`*http.Transport`, so a ticket-authenticated client panicked with no
`Transport`, with a custom `RoundTripper`, and with `WithRetry`. They now take
the TLS config of the `*http.Transport`, looking through `WithRetry`'s
wrapper, so `WithInsecureSkipVerify` and the other TLS options apply to the
WebSocket dial under `WithRetry` too; otherwise they dial with Go's default.
Token-authenticated clients are unchanged: WebSockets still return
`ErrAPITokenWebSocketUnsupported`.
